## A number has a protocol behind it

Accuracy, exact match, pass@k, and perplexity answer different questions. A benchmark must define the examples, the allowed context, the prompt template, the decoding settings, and the aggregation rule. Without those details, two scores can look comparable while measuring different experiments.

## Avoid leakage and selection effects

If evaluation examples appear in pretraining data, a score can reflect memorization rather than generalization. If a benchmark is tuned repeatedly, the test set becomes part of the development loop. Held-out data, contamination checks, and transparent reporting protect the meaning of the result.

## Slice the score

A single average can hide failures by language, task type, difficulty, or response length. Use the board to compare the headline score with slices and baselines. Evaluation is an instrument panel, not a single speedometer.

$$
\text{score} = f(\text{task},\text{data},\text{prompt},\text{metric},\text{baseline})
$$

## Recap

The central idea is **Benchmark design**. The implementation detail matters because it changes what the model can learn, how much memory or compute the system needs, or how confidently we can interpret its behavior. Keep the equation visible, name the controlled variables, and treat every benchmark or safeguard as part of the model’s operating definition.
