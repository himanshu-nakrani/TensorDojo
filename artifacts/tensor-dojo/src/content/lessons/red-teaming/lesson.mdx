## Find failures before users do

A red team does not ask whether the model is generally helpful. It constructs inputs that target a known failure mode: jailbreaks, data leakage, prompt injection, unsafe advice, or misleading confidence. The same model can be safe on ordinary prompts and fail under a small adversarial change.

## The system is the target

Testing only the base model misses tool permissions, retrieval sources, wrappers, memory, and monitoring. A harmless answer can become harmful when the model can send mail, execute code, or expose a private document. Red-team cases should follow the path from input through model output to external effect.

## Turn findings into regression tests

A useful probe becomes a durable test case with a severity, expected behavior, and owner. Mitigations should be evaluated for both attack resistance and false positives. The goal is not a perfect score; it is a measured reduction in unacceptable failure modes.

$$
\text{risk} = \text{likelihood} \times \text{impact}
$$

## Recap

The central idea is **red teaming**: attack success is measured against a named probe (jailbreak, encoding, roleplay) and a known number of defense layers, then turned into a regression test. A single “safe on average” score hides the attack that still gets through at layer 0.
